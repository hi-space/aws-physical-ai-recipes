먼저 용어 — 컨테이너와 Kubernetes

컨테이너 이미지

프로그램과 그것이 필요로 하는 라이브러리를 전부 한 덩어리로 묶은 것입니다. "내 노트북에서는 되는데 서버에서는 안 된다"를 없애는 장치입니다.

이미지를 실제로 실행한 상태를 컨테이너라고 부릅니다.

Kubernetes

컨테이너를 여러 서버에 나눠 띄우고 관리해 주는 시스템입니다. 어느 서버에 띄울지, 죽으면 다시 띄울지를 자동으로 정합니다.

k8s라고 줄여 쓰기도 합니다. 명령은 kubectl로 보냅니다.

파드(Pod)

Kubernetes가 다루는 실행 단위. 보통 컨테이너 1개가 파드 1개입니다. kubectl get pods로 목록을 봅니다.

노드(Node)

파드가 실제로 올라가는 서버 한 대. 여기서는 Amazon EC2 가상 서버가 노드가 됩니다. GPU가 달린 노드가 GPU 노드입니다.

Amazon EKS

AWS가 Kubernetes의 관리 부분(컨트롤 플레인)을 대신 운영해 주는 서비스입니다. 우리는 그 위에 올릴 것만 신경 씁니다.

Helm 차트

Kubernetes에 무엇을 어떻게 띄울지 적은 설치 꾸러미. OSMO도 차트로 설치합니다.

먼저 용어 — AWS 자원과 배포 도구

리전 / 가용 영역

리전은 서울·버지니아 같은 지리적 구역, 가용 영역(Availability Zone)은 그 안의 독립된 데이터센터 묶음입니다. GPU 재고는 가용 영역 단위로 달라집니다.

Amazon VPC / 서브넷

내 계정 전용 가상 네트워크와 그 안의 주소 구획입니다. 인터넷에서 직접 닿을 수 없는 구획을 프라이빗 서브넷이라 부릅니다.

주소 범위(CIDR)

203.0.113.10/32처럼 IP 주소 묶음을 표기하는 방식입니다. /32는 딱 1개 주소를 뜻합니다. 접속 허용 목록에 씁니다.

Terraform과 terraform.tfvars

만들 자원을 코드로 적어 실행하는 도구입니다. .tfvars는 리전·이름 같은 내 환경에 맞는 값만 따로 적는 파일입니다.

멱등(idempotent)

여러 번 실행해도 결과가 같다는 뜻입니다. 실습 중 단계가 실패해도 그 단계부터 다시 돌리면 됩니다.

연기 테스트(smoke test)

기능을 전부 검사하지 않고 일단 켜지는지만 보는 최소 확인입니다. 전원을 넣고 연기가 나는지 보는 데서 온 표현입니다.

모르는 단어가 나오면 그 자리에서 물어보세요. 오늘 목표는 용어 암기가 아니라 배포가 끝까지 도는 것을 눈으로 확인하는 것입니다.

NVIDIA OSMO — 무엇이고 왜 필요한가

OSMO는 무엇인가

Physical AI 개발에서 반복되는 워크플로를 YAML로 정의하고 실행하는 오케스트레이션 프레임워크입니다.

데이터 수집 → 시뮬레이션 → 정책 학습 → 엣지 배포. 이 사이클이 계속 돌면서 각 단계가 서로 다른 컴퓨팅·스토리지·모니터링을 요구합니다.

왜 직접 관리하기 어려운가

  • GPU는 비싸고 항상 켜둘 수 없다 → 필요할 때만 뜨고 사라져야 한다
  • 학습이 12시간 돌 수도 있다 → 중간에 노드가 회수되면 안 된다
  • 산출물(체크포인트, 데이터셋)이 남아야 한다
  • 버전 호환성 — 드라이버·CUDA·프레임워크가 서로 물린다

GPU 노드 특성

장시간 학습 보호

AWS 구성도 ① 사용자는 어떤 길로 들어오는가

실선은 실제 트래픽이 흐르는 길, 점선은 리다이렉트(다른 주소로 넘겨보내기) 또는 우회 경로입니다. 상자 묶음은 그 자원이 어디에 만들어지는가를 나타냅니다.

정상 경로 — 3중 관문

브라우저 → 웹 방화벽(허용 IP만) → Amazon CloudFront → 클러스터 앞의 로드 밸런서 → 게이트웨이 파드가 로그인 검사.

로그인이 안 돼 있으면 게이트웨이가 Amazon Cognito 로그인 화면으로 보내고, 로그인이 끝나면 CloudFront 주소로 되돌아옵니다. 이 왕복 때문에 배포 6단계가 순서 있는 왕복이어야 합니다.

운영자(터미널) 경로는 완전히 별개

kubectl은 CloudFront를 거치지 않고 Amazon EKS 제어 영역에 직접 붙습니다. 기본값이 프라이빗 전용이라, 가상 네트워크 안에서 접속하거나 본인 IP를 허용 목록에 넣어야 합니다.

"배포는 성공했는데 kubectl이 안 된다"의 대부분이 이것입니다.

점선으로 표시한 우회 경로를 알아두세요. 로드 밸런서는 자기 고유 주소를 가지고 있고 80·443 포트가 0.0.0.0/0으로 열려 있습니다. 그 주소로 직접 접속하면 웹 방화벽의 허용 IP 목록을 건너뜁니다. 로그인 검사는 그대로 동작하므로 아무나 들어오지는 못하지만, IP 제한은 유일한 방어선이 아니라 보조 수단으로 봐야 합니다.

AWS 구성도 ② 클러스터 안과 데이터·GPU

화면이 좁으면 그림을 가로로 스크롤할 수 있습니다. 실선은 접근·호출, 점선은 지표 전송입니다. 오른쪽으로 갈수록 클러스터 바깥입니다.

항상 켜져 있는 것

m7i.2xlarge 3대. OSMO 본체·AI 워크로드 스케줄러·Karpenter가 여기 삽니다. 시간당 비용의 대부분이 이 3대입니다.

평소에 비어 있는 것

GPU 노드 칸은 0대가 정상입니다. Karpenter가 워크플로 요청을 보고 만들고, 일이 끝나면 5분 뒤 없앱니다.

비밀 키가 없는 권한

파드가 Amazon S3·ECR·Secrets Manager에 접근하는 권한은 역할로 부여됩니다(IRSA / EKS Pod Identity). 액세스 키를 만들어 넣지 않습니다.

모든 외부 다운로드는 네트워크 주소 변환(NAT) 게이트웨이를 지납니다. GPU 노드가 프라이빗 서브넷에 있으므로 컨테이너 이미지, 사전학습 모델, 데이터셋을 받을 때마다 통과 데이터 GB당 요금이 붙습니다. 이 리포에는 Amazon S3·ECR용 가상 네트워크 엔드포인트(VPC endpoint)가 없어서, 같은 리전 안의 S3 트래픽도 이 경로를 씁니다. 수십 GB짜리 모델을 받으면 인스턴스 요금과 별개로 잡힙니다.

사전 준비 ①-C Windows에서 실습하는 경우

배포 스크립트는 전부 bash 스크립트입니다 (scripts/*.sh, 첫 줄이 #!/usr/bin/env bash). Windows 명령 프롬프트나 PowerShell에서는 그대로 실행되지 않습니다. 아래 두 방법 중 하나를 고르세요.

방법 1 — WSL (권장)

Windows Subsystem for Linux. Windows 안에서 Ubuntu를 돌리는 기능으로, 리눅스 실습 절차를 그대로 따라갈 수 있습니다.

한 번 설치하면 이후는 리눅스와 완전히 동일합니다.

방법 2 — Amazon EC2 리눅스 인스턴스

작은 Amazon EC2 인스턴스(예: t3.small, Amazon Linux 2023)를 띄우고 거기서 실습합니다. WSL 설치 권한이 없는 회사 노트북에 적합합니다.

접속은 AWS Systems Manager Session Manager를 쓰면 SSH 키가 필요 없습니다. 실습 후 인스턴스를 반드시 종료하세요.

방법 1 — WSL 설치 (PowerShell을 관리자로 실행)

# 재부팅 후: 설치 확인 (버전 2 여야 합니다)

deploy-all.sh가 하는 8단계

  1. preflight.sh — 도구·자격증명·설정 파일 확인, terraform validate. 전체를 게이팅합니다. 여기서 막히면 뒤 단계는 시도할 필요가 없습니다.
  2. deploy-infra.sh — infra/core를 감싼 얇은 래퍼. Amazon EKS + Amazon RDS for PostgreSQL + Amazon ElastiCache for Redis + Amazon S3 / Amazon ECR / AWS KMS / IAM Roles for Service Accounts. 가장 오래 걸리는 단계 — Amazon EKS 컨트롤 플레인 생성 자체가 10분 이상입니다.
  3. deploy-karpenter.sh — Karpenter 설치 + GPU NodePool 생성. 여기서 노드가 뜨는 게 아니라, "필요하면 띄울 수 있는 규칙"이 만들어지는 것입니다.
  4. deploy-gpu-operator.sh — NVIDIA GPU Operator. 머신 이미지에 드라이버가 이미 있으므로 드라이버·툴킷 설치는 비활성.
  5. deploy-efa-device-plugin.sh — AWS Elastic Fabric Adapter 디바이스 플러그인. 분산 학습용. Elastic Fabric Adapter 지원 노드가 아직 없어도 미리 설치 가능합니다.

3·4·5는 서로 독립이고 모두 2단계의 클러스터만 필요합니다. 순서를 바꿔도 무방하지만 스크립트는 이 순서로 진행합니다.

8단계 — 6단계가 핵심

  1. deploy-osmo-sso-bootstrap.sh — OSMO + Amazon Cognito 통합 인증(Single Sign-On) + Amazon CloudFront. 내부에서 deploy-kai.sh를 자동 실행합니다(AI 워크로드 스케줄러 (KAI) 설치). 단일 terraform apply로 풀 수 없는 순환 의존성을 깨는 단계.
  2. validate-platform.sh — 클러스터 / OSMO / AI 워크로드 스케줄러 (KAI) / GPU 런타임 점검. 워크플로를 제출하지는 않습니다.
  3. smoke-test.sh — examples/osmo-smoke/workflow.yaml 제출 (CPU 워크플로).

6단계가 푸는 순환 의존성

Amazon CloudFront 는 게이트웨이 로드 밸런서를 오리진(origin) 으로 알아야 한다 │ ▲ ▼ Amazon Cognito 는 CloudFront 도메인을 게이트웨이 로드 밸런서는 콜백(callback) URL 로 알아야 한다 OSMO 를 배포해야 생긴다 ▲ │ └────────────────────────────────────────────┘ 해법 — 4단계로 나눠 실행: ① cognito (임시 도메인으로 먼저 생성) ② deploy-osmo → 게이트웨이 로드 밸런서가 실제로 생김 ③ cloudfront → 그 로드 밸런서를 오리진으로 설정 ④ cognito 재적용 → 진짜 CloudFront 도메인으로 갱신 → deploy-osmo 재적용

이래서 이 단계만 스크립트가 필요합니다. 나머지는 Terraform이나 Helm 한 번으로 끝나지만, 6단계는 순서가 있는 왕복이어야 합니다.

표시용 이름이 아예 없으면 — 최악의 경우

통합 인증 게이트웨이는 표시용 이름이 없으면 고유 번호로 대체합니다. 그러면 화면 오른쪽 위에 UUID가 그대로 뜨고, "내 워크플로"는 user:7a3f9c21-...로 필터돼 영구히 빈 목록이 됩니다.

이 리포는 이 문제를 미리 막아 둡니다. infra/cognito가 초기 관리자를 만들 때 이메일의 @ 앞부분을 자동으로 표시용 이름에 넣습니다 (admin@osmo.local → admin). Terraform으로 만든 사용자는 신경 쓸 필요가 없습니다.

문제는 나중에 손으로 추가한 사용자입니다. AWS 콘솔이나 admin-create-user로 사용자를 만들면 표시용 이름이 비어 있습니다. 그 사용자는 로그인은 되는데 워크플로 목록이 비어 보입니다.

사용자 이름 맞추는 방법 — 실제 명령

1) 지금 값이 어떻게 들어있는지 확인

POOL="$(cd infra/cognito && terraform output -raw user_pool_id)"

aws cognito-idp list-users --user-pool-id "$POOL" \
  --query 'Users[].[Username, Attributes[?Name==`email`].Value | [0], Attributes[?Name==`preferred_username`].Value | [0]]' \
  --output table

세 번째 칸이 비어 있으면 그 사용자가 문제의 사용자입니다.

2) 표시용 이름을 채워 넣기 (권장 해결책)

aws cognito-idp admin-update-user-attributes \
  --user-pool-id "$POOL" \
  --username "gildong@example.com" \
  --user-attributes Name=preferred_username,Value=gildong

여기에 넣을 값을 OSMO 쪽 사용자 이름과 똑같이 맞추세요. OSMO 쪽 이름은 osmo user list로 확인합니다. 두 값이 같아야 웹에서 만든 워크플로와 명령줄 도구로 만든 워크플로가 같은 목록에 나옵니다.

그래서 역할은 관리자가 따로 부여해야 합니다.

비밀번호는 화면에서 물어봅니다(8자 이상, 대·소문자와 숫자 포함). 스크립트가 Amazon Cognito 계정을 만들고, 고유 번호(sub)를 찾아 OSMO 역할까지 부여합니다. 표시용 이름도 자동으로 채웁니다 — 앞 장의 "내 워크플로가 안 보이는" 문제가 원천적으로 안 생깁니다.

이미 있는 사용자에게 다시 실행해도 안전합니다. 계정을 다시 만들지 않고, 빠진 표시용 이름을 채우고 빠진 역할만 추가합니다. 이미 로그인해 버려서 osmo-default만 갖게 된 동료를 고칠 때 그대로 쓰면 됩니다.

사용자 추가 — 자주 묻는 것과 함정

"그냥 회원가입을 열면 편하지 않나요?"

아닙니다. 관리자 일이 줄지 않습니다. 회원가입을 허용해도 역할 부여는 여전히 수동이라, 사용자는 로그인만 되고 워크플로는 못 내는 상태로 들어옵니다. 게다가 로그인 화면에서 직접 가입하면 표시용 이름이 비어 있어서 화면에 알 수 없는 고유 번호가 뜹니다. 얻는 것 없이 잃는 것만 있습니다.

설정 파일에 external_roles 라는 항목이 있어서 회사 계정의 그룹을 OSMO 역할로 자동 연결해 줄 것처럼 보이지만, 이 구성에서는 동작하지 않습니다. 게이트웨이가 역할을 읽는 위치는 로그인 증서(토큰) 안의 roles 항목인데, Amazon Cognito 가 발급하는 증서에는 그 항목이 없습니다. 결국 역할은 OSMO 데이터베이스에서만 옵니다.

Karpenter — 노드를 자동으로 만들고 없애는 담당

이 리포에서 Karpenter를 이해하지 못하면 GPU 워크플로가 왜 Pending인지, 왜 요금이 계속 나가는지 설명할 수 없습니다. 가장 중요한 구성요소 중 하나입니다.

한 줄 정의

Kubernetes에 "이 파드를 놓을 자리가 없다"는 상황이 생기면, 그 파드에 딱 맞는 Amazon EC2 인스턴스를 즉석에서 새로 사서 클러스터에 붙여 주는 프로그램입니다. 일이 끝나 비면 스스로 반납합니다.

AWS가 만든 오픈소스이고, 클러스터 안에서 파드로 동작합니다 (kube-system 네임스페이스, 릴리스 이름 karpenter).

왜 필요한가 — 이 워크숍의 이유

GPU 노드는 비쌉니다. G7e/G6e를 하루 종일 켜 두면 학습을 하지 않는 시간에도 계속 과금됩니다. 그래서 이 리포는 GPU 노드를 미리 만들어 두지 않습니다 — 만드는 규칙만 등록해 두고, 워크플로가 생길 때 Karpenter가 만들게 합니다.

3단계 deploy-karpenter.sh가 끝나도 GPU 노드는 0대입니다. 정상입니다.

Karpenter 설정 — 서버를 주문하는 "양식"과 "규칙"

3단계 deploy-karpenter.sh를 실행해도 GPU 노드는 한 대도 생기지 않습니다. 만들어지는 것은 나중에 노드를 주문할 때 쓸 서류 두 장입니다.

① EC2NodeClass — 주문 양식

"서버를 사면 이런 사양으로 사라"를 적어 둔 종이입니다. 노트북을 살 때의 견적서와 같습니다.

  • 운영체제 이미지 — NVIDIA 그래픽 드라이버가 미리 깔린 것을 특정 버전으로 못박아 씁니다. 그래서 나중에 드라이버를 따로 설치하지 않습니다.
  • 어느 네트워크에 넣을지 — 직접 적지 않고 이름표(태그)로 찾습니다. 네트워크를 나중에 늘려도 이 종이를 고칠 필요가 없습니다.
  • 디스크 1024Gi (약 1TB), 암호화, 서버 반납 시 함께 삭제 — 학습용 이미지와 데이터가 커서 이만큼 잡습니다.

이 양식은 aws-osmo-g7e 딱 한 장이고, 아래 규칙 세 개가 모두 이 한 장을 같이 씁니다.

"어떤 크기까지, 몇 대까지 주문해도 되는가"를 정한 종이입니다. GPU 종류별로 한 장씩 있습니다.

자동 정리가 학습 중인 서버를 반납해 버리면 큰일입니다. 그래서 GPU 학습 작업에는 "이 작업은 건드리지 마세요" 표시를 붙입니다 (karpenter.sh/do-not-disrupt=true). 이게 없으면 Karpenter가 "별로 안 쓰는 서버 같다"고 판단해 몇 시간짜리 학습을 없애 버릴 수 있습니다.

AWS가 서버를 회수하겠다고 예고하면? 그 알림이 전용 대기열 (Amazon Simple Queue Service)로 오고, Karpenter가 그걸 보고 미리 대체 서버를 준비합니다. 이 권한은 Amazon EKS Pod Identity로 부여돼서 비밀 키를 따로 만들 필요가 없습니다.

확인할 때 쓰는 명령 3개

# 1) 서류 두 장이 잘 등록됐는지 (서버 목록이 아닙니다)
kubectl get nodepool,ec2nodeclass

# 2) 지금 주문이 진행 중인 서버가 있는지
kubectl get nodeclaims

# 3) 서버를 못 만들고 있으면 이유가 여기 찍힙니다 (재고 부족 등)
kubectl -n kube-system logs deploy/karpenter --tail=50

GPU 경로 — 노드를 미리 띄워둬야 하는 이유

OSMO는 제출 시점에 pool/platform의 가용 리소스를 검증합니다. GPU 노드가 0대인 상태(scale-to-zero)에서 GPU 워크플로를 제출하면 이렇게 거부됩니다:

There are no resources in platform g6e-l40s and pool default!

즉 노드가 먼저, 제출이 나중입니다. 그래서 GPU 워크플로 제출 전에 짧은 대기용 파드로 GPU 노드를 미리 띄워(prewarm) OSMO에 보이게 만듭니다.

scripts/prewarm-gpu-node.sh
환경변수기본값 / 용도
GPU_PREWARM_INSTANCE_TYPEg7e.2xlarge
GPU_PREWARM_TIMEOUT45m
KARPENTER_NODEPOOL_NAMEKarpenter NodePool 이름 — 인스턴스 타입과 반드시 짝을 맞춰야 합니다

흔한 실수: GPU_PREWARM_INSTANCE_TYPE=g6e.8xlarge만 주고 KARPENTER_NODEPOOL_NAME은 기본값(aws-osmo-g7e)으로 두는 것. 파드가 영원히 Pending입니다. 둘을 함께 지정하세요:

GPU_PREWARM_INSTANCE_TYPE=g6e.8xlarge \
KARPENTER_NODEPOOL_NAME=aws-osmo-g6e \
  scripts/prewarm-gpu-node.sh

제출 직후 이 대기용 파드를 반드시 삭제하세요. 그 파드가 노드의 유일한 GPU를 붙잡고 있으면 정작 학습 워크플로가 SCHEDULING에서 멈춥니다. 실제로 이 함정으로 실습이 막힌 사례가 있습니다.

GPU 용량 — 기본 풀과 폴백

기본 GPU 풀은 g7e-rtx-pro-6000(NVIDIA RTX PRO 6000, 그래픽 메모리 약 96GB)입니다. Amazon EC2 G7e 는 신형 인스턴스 패밀리라 리전·가용 영역별 재고 편차가 큽니다. 못 구하면 g6e-l40s(NVIDIA L40S, 그래픽 메모리 48GB)로 대체(fallback)합니다.

대체 경로를 켜는 방법 — 스위치 2개를 함께

DEPLOY_G6E_NODEPOOL=true \
OSMO_CONFIGURE_G6E_PLATFORM=true \
  scripts/deploy-all.sh

GPU 노드를 만드는 쪽(Karpenter NodePool)과 OSMO가 그 노드를 인식하는 쪽(OSMO 플랫폼)을 둘 다 설정해야 합니다. 하나만 켜면 노드는 뜨는데 OSMO가 모르거나, OSMO는 아는데 노드가 안 뜹니다.

워크플로에서 플랫폼 지정

osmo workflow submit <workflow.yaml> --set platform=g6e-l40s

OSMO 명령줄 도구 버그: --set을 여러 번 쓰면 마지막 것만 적용됩니다. 여러 값을 넘길 때는 하나의 --set에 공백으로 이어 쓰세요.

# 잘못됨 — platform 만 적용됨
--set max_steps=700 --set platform=g6e-l40s

# 올바름
--set max_steps=700 platform=g6e-l40s

배포 전 용량 확인 — 그리고 그 한계

# 이 리전에서 g6e 를 어느 가용 영역(Availability Zone)에 파는가
aws ec2 describe-instance-type-offerings --region "$AWS_REGION" \
  --location-type availability-zone \
  --filters "Name=instance-type,Values=g6e.4xlarge,g6e.8xlarge,g6e.12xlarge" \

aws service-quotas get-service-quota --region "$AWS_REGION" \
  --service-code ec2 --quota-code L-DB2E81BA --query 'Quota.Value' --output text

위 두 확인을 통과해도 노드 생성은 실패할 수 있습니다. 두 명령은 "이 타입을 이 가용 영역에서 파는가"와 "내 서비스 할당량이 충분한가"에만 답하고, 지금 그 가용 영역에 실제 여유 용량이 있는가는 알려주지 않습니다.

용량 부족 오류가 나면 — 단계별 대응

① 인스턴스 크기를 Karpenter가 고르게 한다

prewarm-gpu-node.sh는 인스턴스 타입을 nodeSelector에 박아 검사하므로 대체가 안 됩니다(의도된 설계 — 특정 타입이 뜬다는 증명용). "아무 GPU 노드나" 원하면 Karpenter NodePool 과 GPU 개수만 요청하세요.

NS="$(cd infra/core && terraform output -raw osmo_workload_namespace)"

kubectl -n "$NS" apply -f - <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: aws-osmo-gpu-probe
spec:
  restartPolicy: Never
  nodeSelector:
    karpenter.sh/nodepool: aws-osmo-g6e
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  containers:
    - name: hold
      image: public.ecr.aws/docker/library/busybox:1.36
      command: ["sh", "-c", "sleep 86400"]
      resources:
        limits:
          nvidia.com/gpu: "1"
YAML

② 그래도 안 되면

AWS 오류 메시지가 용량이 있는 가용 영역을 알려줍니다. 하지만 가상 네트워크(Amazon VPC)에 그 가용 영역의 서브넷이 없으면 갈 수 없습니다.

VPC="$(cd infra/core && terraform output -raw vpc_id)"
aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC" \
  --query 'Subnets[].{Id:SubnetId,AZ:AvailabilityZone}' --output table

선택지 3개: 기다리기(용량 부족은 일시적), 서브넷 추가(Terraform 변경), 다른 리전.

서브넷 추가 시 함정: terraform apply가 그동안 쌓인 설정 차이(drift)까지 함께 가져갑니다. 실제 사례에서 같은 실행 계획이 Amazon RDS 엔진 버전을 되돌리고 Amazon EKS 애드온 3개를 건드리려 했습니다. 반드시 전체 변경 목록을 읽고, 범위를 좁히세요:

terraform show /tmp/az.tfplan | grep '^  # '   # 모든 줄을 읽으세요
terraform apply -target=module.vpc             # 서브넷만

  1. "추측하지 말고 파일을 읽어라"고 지시하세요. AI는 학습한 일반 지식으로 그럴듯한 답을 만들 수 있습니다. 이 자료를 만들 때도 어떤 제품명이 무슨 약자인지 물었더니 처음엔 추측하려 했고, 실제 저장소 설명을 확인시키니 "풀어 쓰는 약자가 아니다"가 정답이었습니다. 숫자·버전·기본값은 반드시 파일 근거를 요구하세요.
  2. 프로젝트 규칙은 CLAUDE.md 같은 파일에 적어 두세요. "약어를 쓰지 마라", "커밋은 검증 후에만" 같은 규칙을 매번 말하지 않아도 되게 만듭니다. 같은 지적을 세 번 하고 있다면 그건 규칙 파일에 들어갈 내용입니다.
  3. 검증이 끝나기 전에 커밋하지 마세요. AI는 "일단 커밋하고 나중에 얹자"고 제안하는 경향이 있습니다. GPU 실행 결과처럼 확인에 시간이 걸리는 항목이 남아 있으면 기다리는 게 맞습니다. 중간 상태가 이력에 남으면 나중에 원인 추적이 어려워집니다.
  4. 되돌릴 수 없는 명령은 직접 확인하세요. 특히 terraform.tfvars는 이 리포에서 버전 관리에서 제외돼 있습니다 — 덮어쓰면 git으로 복구할 수 없습니다. AI에게 파일 수정을 맡길 때 이런 파일은 먼저 백업하세요.
  5. 자격증명을 대화창에 붙여 넣지 마세요. 임시 접근 키, 비밀번호, NVIDIA GPU Cloud 접근 키가 대화 기록에 남습니다. 필요한 건 프로필 이름(AWS_PROFILE=...)일 뿐, 키 값 자체가 아닙니다. 도구 설정 파일에 키가 저장되지 않는지도 확인하세요.
  6. 틀린 진단은 기록해 두세요. "이 가설은 확인해 봤고 아니었다"를 남기지 않으면 다음에 같은 길을 또 갑니다. 이 리포에서도 학습 실패 원인 가설 두 개를 각각 반증한 기록을 남겨 두고 있습니다.

한 줄 요약: AI 도구는 읽기·추적·반복 작업에서 사람보다 빠르고, 예측·판단·되돌릴 수 없는 작업에서는 사람을 대신할 수 없습니다. 이 경계를 지키면 오늘 같은 배포를 훨씬 빨리 끝낼 수 있습니다.
