NVIDIA OSMO on AWS — 사용자가 쓰는 것은 무엇인가

OSMO는 로봇·자율주행 개발에서 반복되는 작업을 YAML 파일 한 장으로 정의해 실행하는 도구입니다. 데이터 준비, 시뮬레이션, 학습, 평가를 같은 방식으로 제출합니다.

사용자가 하는 일

  • 워크플로 파일을 쓴다 — 어떤 컨테이너 이미지로, 어떤 명령을, 어떤 크기의 장비에서 돌릴지
  • 제출한다 — osmo workflow submit
  • 결과를 받는다 — 출력 데이터셋과 기록 파일

장비를 직접 빌리거나 컨테이너를 띄우는 일은 하지 않습니다.

플랫폼이 대신 하는 일

  • 요청한 크기의 GPU 장비를 필요할 때만 생성하고, 종료 후 회수한다
  • 여러 GPU가 필요한 학습은 전부 준비될 때까지 기다렸다가 시작한다
  • 단계 사이에 산출물을 이름으로 넘긴다
  • 기록과 지표를 한곳에 모아 둔다

AWS 인프라 전체이 리포(osmov2) 이미 배포돼 있음 — 사용자는 구성하지 않습니다

이 리포는 OSMO 자체를 포함하지 않습니다. OSMO는 버전을 고정해 가져다 쓰는 외부 구성 요소이고, 리포가 소유하는 것은 AWS 쪽 구성과 워크플로 예제입니다.

구축자 관점과 사용자 관점의 차이

같은 시스템이지만 책임의 경계가 다릅니다. 사용자는 구축 영역의 내부를 알지 못해도 되지만, 그 영역에서 발생한 장애의 증상은 구분할 수 있어야 합니다.

설치자 (지난 교육)

플랫폼 구축

  • Terraform으로 네트워크·클러스터·데이터베이스 생성
  • Karpenter 노드 규칙, GPU 드라이버 설치
  • OSMO 설치와 통합 인증 연결
  • 사용자 계정 생성과 권한 부여
  • 비용과 용량을 책임진다
사용자 (오늘)

플랫폼 활용

  • 로그인해서 자기 신분을 증명
  • workflow.yaml 한 개를 작성
  • 제출하고, 상태와 로그를 본다
  • 결과물(체크포인트·데이터셋)을 받는다
  • 노드를 직접 만들지 않는다

정리

YAML 하나를 제출하면, 그 뒤의 노드 확보·스케줄링·드라이버·저장소는 플랫폼이 처리한다. 사용자가 지정하는 것은 "무엇을 얼마나 쓸지"(resource)와 "무엇을 실행할지"(image + command)뿐이다.

그래서 사용자 교육의 대부분은 YAML의 의미와 결과를 읽는 방법입니다. 쿠버네티스 명령을 외울 필요는 없습니다.

사용자 관점 필수 용어

용어사용자에게 어떤 의미인가
워크플로 (workflow) 제출 단위. YAML 파일 한 개가 워크플로 한 개입니다. 안에 태스크가 여러 개 들어갈 수 있습니다
태스크 (task) 컨테이너가 한 번 실행되는 단위. 데이터 준비 · 학습 · 평가처럼 단계별로 구분합니다
컨테이너 이미지 (image) 코드 실행 환경을 그대로 고정한 패키지. 파이썬 버전과 라이브러리가 포함됩니다
리소스 (resource) 이 태스크에 줄 CPU·메모리·GPU·디스크의 양. YAML 상단에 이름을 붙여 정의하고 태스크가 참조합니다
플랫폼 (platform) 어떤 종류의 하드웨어에서 돌릴지 고르는 이름표. 예: g7e-rtx-pro-6000. 사용자가 인스턴스 타입을 직접 쓰지 않는 이유입니다
풀 (pool) 같은 성격의 자원 묶음. 대기열과 기본 제한 시간이 여기에 걸려 있습니다
데이터셋 (dataset) OSMO가 관리하는 입출력 저장 단위. 태스크의 결과물을 다음 태스크에 넘길 때 씁니다
대기열 제한 시간 / 실행 제한 시간 순서를 기다릴 수 있는 최대 시간 / 실행될 수 있는 최대 시간. 둘 다 초과하면 자동 종료됩니다

약어 대신 정식 명칭 — 이 자료에서 GPU는 그래픽 처리 장치(Graphics Processing Unit), 통합 인증은 Single Sign-On, 명령 줄 도구는 Command Line Interface(CLI)를 가리킵니다. 처음 나올 때 한 번씩 풀어 씁니다.

플랫폼 도입 전 연구 환경의 제약 5가지

P1

GPU 할당 경직

연구원별로 GPU를 고정 할당 → 추가 확보 불가

P2

환경 불일치

연구원마다 학습 환경과 절차가 달라 재현 불가

P3

관측 미흡

실험 추적·자원 사용률을 개별로 확인

P4

분산 학습 제한

클러스터 구성이 없어 여러 대로 늘리기 어려움

P5

GPU 증설 지연

신규 장비 도입에 오랜 기간 소요

제약이 사용자에게 드러나는 형태 — P1과 P5는 GPU 확보 불가, P2는 실행 결과의 재현 불가, P3는 성능 저하 원인 파악 불가로 나타납니다. 이후 슬라이드의 기능은 각각 이 증상에 대응합니다.

플랫폼 요구사항 4가지

데이터 준비부터 강화학습·정책 모델 학습, 시뮬레이션 평가, 엣지 배포까지 전 과정을 여러 연구원이 공유하는 환경에서 실행하기 위해 아래 네 가지가 요구되었습니다. R1에서 R4로 갈수록 상위 계층입니다.

R1

독립 실행 환경 동시 제공

데이터 변환, 시뮬레이션 학습, 정책 모델 학습, 평가가 각각 다른 컨테이너 이미지를 쓰므로, 연구원별로 독립된 실행 환경을 동시에 제공

R2

우선순위와 GPU 할당량

단계별 GPU 요구량이 크게 다르므로(데이터 준비는 CPU만, 정책 모델 학습은 GPU 1장, 영상 증강은 대용량 메모리) 작업별 우선순위와 할당량이 필요

R3

작업 대기열 관리

여러 연구원의 학습·평가 작업이 동시에 몰릴 때 대기열(queue)을 관리하는 스케줄러

R4

파이프라인 오케스트레이션

R1–R3를 묶어 단계 간 데이터 전달과 제출·복원을 자동화하는 계층 (NVIDIA OSMO)

단계별 요구 특성 — 데이터 준비는 CPU와 네트워크 대역, 강화학습과 정책 모델 학습은 GPU와 장시간 실행, 시뮬레이션 평가는 GPU와 그래픽 라이브러리, 엣지 배포는 산출물 반출 경로를 필요로 합니다. 요구가 서로 달라 단계마다 자원을 따로 지정할 수 있어야 합니다.

Amazon EKS 선택 근거

결론부터 정리하면, 이 플랫폼은 관리형 쿠버네티스 기반이며 그 결과 OSMO를 수정 없이 사용할 수 있습니다.

후보성격이 요구사항에서의 판단
Amazon EKS (채택) 관리형 쿠버네티스. 스케줄러는 쿠버네티스 기본 + AI 워크로드 스케줄러(KAI) + Karpenter OSMO가 네이티브로 올라감. 장애 복원은 직접 구성해야 함
SageMaker HyperPod 관리형 학습 클러스터. Slurm 또는 EKS 모드 노드 장애 시 자동 교체가 강점 — 장기·대규모 안정 학습에 적합
AWS Batch 관리형 배치 처리 운영 부담이 가장 낮지만 멀티노드 분산이 번거롭고 OSMO 통합이 어려움
AWS ParallelCluster 전통 고성능 컴퓨팅(HPC) 방식, Slurm Message Passing Interface 기반 HPC에는 맞지만 이 용도에는 비권장

실제 채택은 조합입니다 — 컨트롤 플레인은 EKS, 장기·대규모 안정 학습은 SageMaker HyperPod를 EKS 모드로 GPU 풀 하나로 편입, 대량 병렬 시뮬레이션은 Batch를 보조로. 이 환경에는 EKS와 온디맨드 GPU만 있습니다 — 선택 방법은 뒤의 "GPU 풀 선택"에서 다룹니다.

1단계 — 제약별 해결 수단

제약 하나에 해결책 하나가 대응합니다. 사용자에게 보이는 변화까지 함께 확인하면 각 기능을 어떤 제약 때문에 도입했는지 확인할 수 있습니다.

제약도입한 것사용자에게 보이는 변화
P1 독립 컨테이너·다수 연구원 Amazon EKS + 통합 인증(원 사례는 Keycloak, 이 리포는 Amazon Cognito) 내 작업이 남의 작업과 섞이지 않음. 로그인한 신분으로 내 것만 조회
P2 우선순위·GPU 할당량 AI 워크로드 스케줄러(KAI)의 공정 분배 + OSMO의 할당량 중앙 관리 GPU가 없을 때 무한정 실패하지 않고 순서를 기다림
P3 작업 대기열 관리 계층형 대기열 → 우선순위·할당량에 따라 자동 디스패치 제출 시점에 자리가 없어도 제출은 성공하고, 자리가 나면 실행됨

역할 분담 — 정책과 제출은 OSMO, 실행과 대기열은 AI 워크로드 스케줄러(KAI), 신분 확인은 통합 인증. 사용자가 쓰는 도구는 OSMO 하나입니다.

2단계 — 실험 추적과 관측

사용자가 가장 자주 사용하는 단계입니다. 제출은 한 번이지만 상태 확인은 여러 번 반복하기 때문입니다.

실험 추적

하이퍼파라미터와 지표를 실행 단위로 기록해 설정 간 성능을 비교합니다 (원 사례: MLflow)

실시간 관측

GPU 사용률과 학습 진행 상황을 대시보드에서 확인합니다 (Prometheus + Grafana)

장기 로그 분석

장시간 학습에서 발생하는 대량 로그를 질의로 검색합니다. OSMO 기본 로그 조회를 보완하는 계층 (원 사례: ClickHouse)

이 리포(osmov2)에는 관측 구성(Prometheus + Grafana)이 포함되어 있고, 실험 추적과 장기 로그 분석은 포함되지 않습니다. 이 환경에서 지표는 OSMO의 상태·로그 조회로 확인합니다.

2단계 아키텍처 — 구성 요소 배치

사용자 요청 경로

연구원 → (전용 회선 또는 인터넷) → 로드 밸런서 → CPU 노드의 OSMO 서비스. 사용자는 GPU 노드에 직접 접속하지 않습니다.

결과물 저장 위치

산출물과 체크포인트는 객체 저장소(Amazon S3), 메타데이터는 관계형 데이터베이스(Amazon RDS), 세션은 캐시(Amazon ElastiCache), 컨테이너 이미지는 레지스트리(Amazon ECR)

확인 사항 — 학습 종료 후 노드가 회수되어도 결과물은 객체 저장소에 남습니다. 노드가 사라진 뒤 결과물을 찾는 경로는 데이터셋 · 산출물 목록입니다.

3단계 — 사용자 관점의 변경 지점

같은 학습을 서로 다른 자원에서 실행한 세 가지 예시입니다.

차이는 platform 값 한 줄뿐이며, 태스크 정의는 변경하지 않습니다.

클라우드 온디맨드
resources:
  train:
    cpu: 8
    gpu: 1
    memory: 64Gi
    platform: g7e-rtx-pro-6000
다른 GPU 세대
resources:
  train:
    cpu: 8
    gpu: 1
    memory: 64Gi
    platform: g6e-l40s
GPU 없이 (CPU 태스크)
resources:
  prep:
    cpu: 2
    memory: 4Gi
    storage: 4Gi
    # platform 생략

플랫폼 이름표는 관리자가 등록해 둔 것만 쓸 수 있습니다. 현재 사용 가능한 자원은 osmo resource list, 풀은 osmo pool list로 확인합니다.

사용자가 쓰는 것 플랫폼이 알아서 하는 것 ───────────────── ──────────────────────────────────────────── platform: 이름 → 그 이름에 맞는 인스턴스 종류 선택 gpu: 1 → GPU 드라이버가 준비된 노드 확보 image: ... → 레지스트리에서 이미지 내려받기 command / args → 컨테이너 안에서 실행 outputs: → 결과물을 객체 저장소에 보관

인스턴스 타입을 외우지 않아도 되는 이유 — 플랫폼 이름표가 그 매핑을 감싸고 있습니다. 관리자가 노드 종류를 바꿔도 사용자의 YAML은 그대로입니다.

CPU 노드와 GPU 노드의 역할 분리

제출 후 대기 시간이 발생하는 이유를 설명하는 구분입니다.

CPU 노드 (상시 가동)

OSMO 서비스, 스케줄러, 관측 도구, 인증이 배치됩니다. 이 노드가 동작해야 로그인과 제출, 조회가 가능합니다. 상시 가동이므로 비용이 낮은 사양을 사용합니다.

GPU 노드 (필요 시 기동)

학습과 시뮬레이션 실행에만 사용합니다. 작업이 없으면 회수됩니다. 그래서 GPU 워크플로의 첫 제출은 노드가 뜨는 시간을 기다립니다.

사용자가 경험하는 차이 — ① 웹 콘솔은 상시 즉시 응답합니다(CPU 노드). ② GPU 워크플로는 제출 직후 몇 분간 대기 상태에 머무릅니다(노드 확보). 후자는 장애가 아닙니다.

제출부터 결과 등록까지 전체 흐름

① YAML 제출

사용자가 직접 수행하는 단계

② 클러스터 기동

노드 확보와 구성은 자동

③ 분산 학습

여러 GPU에 나눠 실행

④ 실시간 관측

진행 상황과 GPU 사용률

⑤ 결과·모델 등록

체크포인트와 최종 모델 보관

도입 효과

비용 절감

작업 특성에 맞는 GPU 선택으로 동일 예산에서 실험 횟수 증가

유휴 비용 제거

작업이 없으면 GPU 노드가 0 — 미사용 시 GPU 비용이 발생하지 않음

탐색 속도

여러 설정을 동시에 돌려 좋은 모델까지의 시간 단축

사용자가 관여하는 항목은 두 가지입니다 — 작업 특성에 맞는 풀 선택, 체크포인트를 저장하는 코드 작성. 나머지는 플랫폼이 처리합니다.

구성 요소별 역할 지도

앞에서 언급된 구성 요소를 계층별로 정리했습니다. 사용자가 직접 사용하는 것은 최상단 오케스트레이션 계층 하나입니다.

오케스트레이션 · 스케줄링

워크플로 제출과 실행 순서를 담당. 사용자가 직접 쓰는 계층입니다 — OSMO만 직접 쓰고, 그 아래 스케줄러와 노드 자동 확보는 보이지 않습니다.

관측 · 실험 관리

GPU 사용률은 자동으로 올라가지만, loss 같은 학습 지표는 워크플로가 직접 내보내야 표시됩니다. 대시보드 주소는 관리자로부터 전달받습니다. 이 리포는 Prometheus + Grafana 포함

접근 · 운영 · 인프라 정의

로그인과 인프라 구성. 사용자는 로그인만 만나고 나머지는 관리자 영역입니다.

구성 요소를 암기할 필요는 없습니다. 장애 발생 시 사용자가 대응 가능한 계층인지 판단하는 기준으로 활용하며, 뒤의 실패 시 점검 순서와 연결됩니다.

AWS 관리형 서비스의 역할

사용자에게 직접 노출되지 않는 영역이며, 운영 부담이 적은 이유입니다.

컴퓨팅 · 운영

관리형 쿠버네티스와 GPU 인스턴스, 컨테이너 이미지 저장소, 비밀 값 관리. 버전 올리기와 패치를 직접 하지 않습니다

네트워크

사설 네트워크, 온프레미스 연결 전용 회선, 노드 간 고속 통신 장치

스토리지

학습 중 고속 접근용 파일 시스템, 체크포인트·모델 영구 보관용 객체 저장소

사용자에게 오는 이점 — 결과물이 노드와 무관하게 남고, 노드가 죽어도 다시 제출하면 되고, 저장소 용량을 미리 신청할 필요가 없습니다.

OSMO에 접속하는 두 가지 방법 — 웹 콘솔과 명령 줄

이후 내용은 직접 실행하는 절차입니다. 관리자가 계정을 발급한 상태를 전제로 진행합니다.

웹 콘솔 (브라우저)

  • 워크플로 목록과 상태 확인
  • 로그 보기
  • 결과물(데이터셋) 확인 — Datasets 페이지
  • 제출은 명령 줄 도구가 편합니다

명령 줄 도구 (osmo CLI)

  • 워크플로 제출 — 실제 작업의 시작점
  • 상태 조회, 로그 조회
  • 스크립트로 자동화 가능
  • 제출과 조회의 주 경로

사전 준비 — 관리자에게 받을 항목

  1. 계정 — 이메일과 비밀번호. 회원가입은 막혀 있어 관리자만 생성할 수 있습니다
  2. 웹 콘솔 주소 — 콘텐츠 전송 네트워크(CloudFront) 도메인
  3. 접속 허용 — 내 사무실/집의 나가는 공인 IP 주소가 웹 방화벽 허용 목록에 등록되어 있어야 합니다

가장 흔한 첫 실패 — 허용 목록에 IP가 없으면 로그인 화면 자체가 열리지 않습니다(403 Request blocked). 그런데 명령 줄 로그인은 성공했다고 보고합니다 — 인증은 사용자 풀에 직접 붙어 허용 목록과 무관하기 때문입니다. 실패는 다음 명령을 실행할 때 확인됩니다.

실습 파일 준비 — scripts/…의 출처와 실행 위치

이후 사용하는 scripts/와 예제 워크플로 파일은 단일 리포지토리에 포함되어 있습니다. 리포지토리를 clone한 후 지정된 디렉터리로 이동해 명령을 실행합니다.

③ 워크플로 YAML 구조 이해

가장 단순한 형태의 워크플로입니다. 이 항목들을 이해하면 나머지 예제는 같은 구조의 확장입니다.

workflow:
  name: aws-osmo-smoke          # 워크플로 이름
  resources:
    default:                    # 자원 묶음에 이름을 붙임
      cpu: 1
      memory: 2Gi
      storage: 1Gi
  tasks:
    - name: hello
      resource: default         # 위에서 정의한 이름을 참조
      image: public.ecr.aws/docker/library/ubuntu:24.04
      command: ["bash", "-lc"]
      args:
        - |
          set -euo pipefail
          echo "hello from AWS OSMO smoke workflow"
          uname -a

읽는 순서

  1. resources — 얼마나 쓸지 먼저 정의
  2. tasks — 무엇을 실행할지
  3. resource:로 둘을 연결

GPU 사용 시 추가 항목

gpu: 1
platform: g7e-rtx-pro-6000

추가되는 항목은 이 두 줄이며, 나머지 구조는 동일합니다. 다만 GPU 노드는 재고 상황에 따라 확보되지 않을 수 있어 이 과정에서는 CPU 워크플로를 기준으로 설명합니다.

다단계 파이프라인 — 태스크 연결 구조

실제 작업은 데이터 준비 → 학습 → 평가 순으로 이어집니다. 하나의 YAML 안에서 앞 태스크의 결과를 다음 태스크가 입력으로 받습니다.

  tasks:
  - name: inspect-dataset
    resource: cpu_small
    args:
    - |
      mkdir -p {{output}}/dataset          # 결과를 쓸 위치
      ...
    outputs:
    - dataset:
        name: {{ prepared_dataset }}
        path: dataset

  - name: train-policy
    resource: gpu_g7e                      # 이 태스크만 GPU
    args:
    - |
      cp {{input:0}}/dataset/manifest.json ...   # 앞 결과를 입력으로
    inputs:
    - task: inspect-dataset                # 의존 관계 선언

{{output}}

이 태스크의 결과를 저장할 디렉터리. 플랫폼이 경로를 주입합니다

{{input:0}}

첫 번째 입력의 경로. inputs 순서와 대응됩니다

inputs: task:

실행 순서를 만드는 선언. 앞 태스크가 끝나야 시작됩니다

비용 관점 — 데이터 준비는 CPU 자원, 학습은 GPU 자원으로 분리하면 GPU 점유 시간이 줄어듭니다. 태스크를 분리하는 이유입니다.

예제 파이프라인 — 데이터 준비부터 로봇 배포까지 6단계

리포의 e2e-pipeline-examples/는 앞에서 설명한 구조를 적용한 예제입니다. 각 단계의 결과 데이터셋이 다음 단계의 입력 데이터셋으로 연결됩니다.

각 단계는 따로도 돌아갑니다. 3단계만 다시 돌리고 싶으면 1단계가 만들어 둔 데이터셋 이름을 입력으로 주면 됩니다. 전체를 다시 돌릴 필요가 없습니다.

1단계 — 데이터 준비 (CPU 전용)

공개된 로봇 시연 데이터를 내려받아 학습이 요구하는 형식으로 변환하고, 결과를 데이터셋으로 등록합니다.

osmo workflow submit e2e-pipeline-examples/01-data-prep/workflow.yaml \
  --set hf_dataset_id=LightwheelAI/leisaac-pick-orange

단계 수행 내용

  1. Hugging Face(공개 모델·데이터 저장소)에서 시연 데이터 내려받기
  2. LeRobot 데이터 형식 v3.0 → v2.1 변환 (학습 코드가 읽는 버전)
  3. 형식 검사 후 {{output}}/artifacts에 정리

결과 데이터셋 출력 선언

outputs:
- dataset:
    name: {{ output_dataset }}
    path: artifacts

path는 {{output}} 아래의 상대 경로입니다. 이 폴더만 데이터셋으로 올라갑니다.

CPU 자원을 사용하는 이유 — 다운로드와 형식 변환에는 GPU가 필요하지 않습니다. 이 단계를 GPU 자원으로 묶으면 다운로드에 소요되는 30분 동안 GPU 요금이 발생합니다. 단계를 분리하는 이유입니다.

자원 선언

cpu: 16
memory: 96Gi

storage가 큰 이유는 기반 모델 가중치와 중간 체크포인트가 함께 올라가기 때문입니다.

학습량 산정 기준 — 걸음 수가 아닌 샘플 수

기준: global_batch_size × max_steps = 학습이 본 샘플 수. 예제 데이터가 약 10,000 샘플이므로 이 값을 10,000으로 나누면 대략 몇 바퀴 돌았는지가 나옵니다. GPU 1장(L40S) 실측:

global_batch_size초/걸음초당 샘플약 1바퀴 소요
10.392.54약 66분
83.902.05약 81분
326.664.81약 35분

기본값은 스모크용입니다 — max_steps: 10은 파이프라인이 도는지 확인하는 값입니다. 성능이 나오는 모델을 원하면 반드시 올려 잡고, 그만큼 exec_timeout도 함께 늘리세요.

메모리가 노드 크기를 정하는 경우

2·4단계는 memory: 90Gi라서 g6e.2xlarge(64GB)에 배치되지 않습니다. GPU는 여유가 있어도 메모리 때문에 한 단계 큰 노드가 필요합니다.

예제의 기본값은 platform: g6e-l40s(NVIDIA L40S, 그래픽 메모리 48GB)입니다. 부족하면 --set platform=g7e-rtx-pro-6000(RTX PRO 6000, 96GB)으로 바꿉니다 — 큰 배치 학습, 고해상도 영상 증강에서 필요합니다. 요청량은 그대로 두고 이름표만 바꿉니다.

실측 소요 시간 — 준비 시간이 예산을 지배합니다

2026-08-11 측정. GPU 1장(L40S), 시연 60편 데이터셋, global_batch_size: 1, max_steps: 10000 기준입니다.

태스크실제 작업 전 준비 시간작업 자체
데이터 준비무시할 수준 약 1.5분 (시연 60편 → 학습 형식, 666MiB)
미세조정약 7분 — 컨테이너 이미지 받기, 학습 코드 받기, 기반 모델(30억 변수) 내려받기 초당 2.54샘플 → 10,000걸음에 약 66분
평가약 13분 — 시뮬레이터 패키지 설치, 장면 자료 내려받기 1회당 약 4분20초 → 기본 5회에 약 22분

준비 시간은 학습량과 무관하게 매번 듭니다. 그래서 기본값인 10걸음 확인용 실행도 미세조정 태스크에서 약 8분을 씁니다. 준비 시간만 합쳐 약 48분이라, 2시간 안에 끝내야 하는 실행은 학습 루프에 약 70분을 쓸 수 있습니다.

노드를 키워도 학습은 빨라지지 않습니다

측정은 g6e.16xlarge에서 했지만, 병목이 GPU 1장이라 권장 크기인 g6e.8xlarge와 차이가 없었습니다. 남는 것은 쓰지 않는 vCPU뿐입니다.

중간 저장 간격 — 용량과의 절충

중간 결과가 필요 없다면 save_steps를 max_steps와 같게 두세요. 한 번 저장할 때마다 약 10GB입니다. 반대로 긴 학습은 중간 저장이 없으면 제한 시간에 잘릴 때 전부 유실됩니다.

6단계 영상 증강 — 시간을 좌우하는 설정값 하나

영상 생성은 이 파이프라인에서 가장 무거운 작업입니다. 실행 시간이 num_steps(생성 반복 횟수)에 거의 비례합니다.

num_steps시연 1편당용도
35 (기본값)약 80분학습에 쓸 고품질 증강
15약 35분빠른 반복 · 동작 확인
10약 23분파이프라인만 확인

전체 데이터셋을 기본값으로 실행하면 제한 시간 내에 완료되지 않습니다. 클립 120편 × 80분은 약 160시간이고, 이 단계의 실행 제한 시간은 3d(72시간)입니다. 선택지는 세 가지 — 일부 시연만 돌리기, num_steps 낮추기, 제한 시간 올리기.

osmo workflow submit e2e-pipeline-examples/06-cosmos-augment/workflow.yaml \
  --set num_steps=15 resolution=480 input_dataset=e2e-pipeline-lerobot-dataset

해상도도 함께 낮출 수 있습니다

resolution=480은 한 묶음당 계산량과 그래픽 메모리를 함께 줄입니다. 화질은 떨어지므로 동작 확인용입니다.

그래픽 메모리 부족이 나는 단계

해상도·프레임 수가 높으면 48GB 장비에서 메모리 부족으로 실패할 수 있습니다. 이때는 --set platform=g7e-rtx-pro-6000으로 96GB 장비를 씁니다.

체인에서 달라지는 점 3가지

연결 기준 — 데이터셋 이름 대신 태스크 이름

- name: gr00t-finetune
  inputs:
  - task: prepare

앞 태스크의 출력 폴더가 그대로 다음 태스크에 붙습니다.

변수 이름의 단계별 접두사

prep_cpu: 4
train_cpu: 16
eval_cpu: 8

변수 공간이 YAML 하나에 하나뿐이라, 접두사가 없으면 세 단계의 cpu가 서로 덮어씁니다.

제한 시간은 하나로 합산

exec_timeout: 20h — 세 단계 합계에 노드 확보 시간까지 더해 잡습니다. 한 단계라도 남으면 전체가 잘립니다.

묶어도 GPU를 낭비하지 않는 이유 — 자원은 태스크 단위

한 파일에 세 단계를 넣으면 가장 큰 요청량이 전체에 적용될 것처럼 보입니다. 그렇지 않습니다 — 자원은 워크플로가 아니라 태스크마다 따로 배정됩니다.

세 벌을 미리 정의하고 태스크가 골라 씁니다

resources:
  prep_cpu:   { cpu: 4,  memory: 16Gi }   # gpu 항목 없음
  train_gpu:  { cpu: 16, gpu: 1, memory: 96Gi }
  eval_gpu:   { cpu: 8,  gpu: 1, memory: 90Gi }

tasks:
- name: prepare        resource: prep_cpu
- name: gr00t-finetune resource: train_gpu
- name: eval           resource: eval_gpu

결과 — 단계별로 3번 제출한 것과 같습니다

  • 1단계 데이터 준비는 gpu 항목이 없어 CPU 노드에서 실행됩니다
  • GPU는 학습 태스크가 시작될 때 붙고, 끝나면 놓습니다
  • 평가 태스크는 다시 새로 GPU를 받습니다

태스크마다 별도 파드로 뜨기 때문에, GPU 점유 시간이 단계별 제출과 동일합니다.

그러면 묶었을 때 실제로 손해 보는 것은

항목단계별 제출 (3회)단일 제출 (체인)
GPU 점유차이 없음 — 필요한 태스크에만 붙습니다
노드 확보 대기매 제출마다 발생 한 번 뜬 노드를 이어 쓸 수 있어 오히려 유리
제한 시간단계별로 따로 합계 하나 — 넉넉히 잡아야 함
일부만 재실행가능 처음부터 — 단독 버전(03·04)을 씁니다

단계별 워크플로도 같은 구조입니다 — 태스크가 하나뿐이라 resources:에 gpu 한 벌만 있습니다. 체인은 그 정의가 세 벌로 늘어난 것이며, 배정 방식은 동일합니다.

  • prep_cpu → platform: default로 GPU가 없습니다
  • train_gpu → memory: 96Gi · storage: 256Gi

아래쪽 timeout 항목에서 exec_timeout: 20h · queue_timeout: 6h도 그대로 확인됩니다.

outputs 항목의 dataset.name이 결과가 올라갈 데이터셋 이름입니다 — 위 화면에서는 aws-osmo/e2e-vla-chain-closeloop-artifacts.

GPU 워크플로 — 노드가 먼저, 제출이 나중

GPU 노드가 0대면 제출은 대기하지 않고 즉시 거부됩니다 — There are no resources in platform g6e-l40s and pool default!

GPU 노드가 0대일 때만 생기는 일입니다. OSMO는 이미 등록된 자원만 보고 제출을 검사하는데, 노드 자동 확장은 대기 중인 파드가 생긴 뒤에야 노드를 만듭니다 — 노드가 없으면 제출이 거부되고, 제출이 없으면 노드가 생성되지 않습니다. 생성된 노드도 비어 있으면 5분 후 회수됩니다.

① AWS 계정 쪽 — 접속 정보를 받아오는 권한

aws eks update-kubeconfig는 내부적으로 클러스터 정보 조회 한 번만 호출합니다. 그래서 필요한 것도 한 줄입니다.

{
  "Effect": "Allow",
  "Action": "eks:DescribeCluster",
  "Resource": "arn:aws:eks:<리전>:<계정>:cluster/<클러스터>"
}

EC2·GPU 관련 권한은 필요 없습니다. 실제로 장비를 만드는 것은 클러스터 안의 노드 자동 확장 구성 요소이고, 그쪽은 자기 전용 역할로 EC2를 호출합니다.

② 클러스터 쪽 — 접근 항목(access entry) 등록

계정 권한이 있어도 클러스터에 이름이 등록돼 있지 않으면 모든 kubectl 명령이 거부됩니다. 관리자가 한 번 등록합니다.

aws eks create-access-entry --cluster-name <클러스터> \
  --principal-arn <연구원 역할 ARN>
aws eks associate-access-policy --cluster-name <클러스터> \
  --principal-arn <연구원 역할 ARN> \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
  --access-scope type=namespace,namespaces=osmo-workflows

이 조합은 osmo-workflows 이름공간 안에서만 파드를 만들고 지울 수 있게 합니다. 클러스터 전체 권한은 아닙니다.

이름공간 범위만으로는 4번의 확인 단계가 막힙니다 — 정리 스크립트가 노드와 NodeClaim이 사라졌는지 확인하는데, 이 둘은 이름공간에 속하지 않는 클러스터 전체 자원입니다. 읽기만 추가하려면 AmazonEKSAdminViewPolicy를 type=cluster로 함께 붙입니다 — 비밀 값까지 다 보이므로 조직 정책을 먼저 확인하세요.

워크플로 종료 후 GPU 노드를 유지하는 방법 — 디버깅 목적

워크플로 종료 후 정리 스크립트가 대기용 파드를 삭제하면 노드가 빈 상태로 판정되어 5분 후 회수됩니다. 노드가 회수되면 kubectl exec, nvidia-smi, 노드 로컬 파일 확인 등 노드에 접속해서 수행하는 진단이 불가능합니다.

방법 A — 대기용 파드 유지 (권장)

대기용 파드는 sleep만 수행하며 GPU를 요청하지 않습니다. 이 파드가 유지되면 노드가 빈 상태로 판정되지 않아 회수 대상에서 제외됩니다. 정리 스크립트 실행을 진단 완료 후로 미루면 됩니다.

# 진단 중 — 노드 유지 여부 확인
kubectl get nodes -L node.kubernetes.io/instance-type

# 진단 완료 후 회수
scripts/wait-gpu-node-cleanup.sh

클러스터 전역 설정을 변경하지 않는다는 점이 장점입니다. 다만 파드 유지 기간만큼 GPU 인스턴스 비용이 발생합니다.

방법 B — 회수 대기 시간 연장 (관리자)

회수 대기 시간은 노드 자동 확장 설정인 consolidateAfter이며 기본값은 5분입니다. 이 교육 환경의 GPU NodePool 두 개 모두 5m입니다.

kubectl patch nodepool aws-osmo-g6e --type merge \
  -p '{"spec":{"disruption":{"consolidateAfter":"2h"}}}'

# 진단 완료 후 기본값으로 복원
kubectl patch nodepool aws-osmo-g6e --type merge \
  -p '{"spec":{"disruption":{"consolidateAfter":"5m"}}}'

NodePool 단위 설정이므로 같은 풀을 사용하는 다른 워크플로에도 적용됩니다. 관리자와 협의 후 변경하십시오.

연장 가능 시간의 상한은 24시간입니다 — 노드에는 expireAfter: 24h가 별도로 적용되며, 운영체제 보안 패치 반영을 위한 교체 주기입니다. 또한 consolidateAfter: Never는 사용하지 마십시오 — 복원을 누락하면 GPU 인스턴스 비용이 계속 발생합니다.

GPU를 확보하지 못하는 경우 — 여유 용량은 사전에 확인할 수 없습니다

GPU 장비는 리전·가용 영역별로 재고 편차가 큽니다. 제출이 거부되거나 노드 생성이 실패하는 일은 설정 오류가 아닌 경우가 많습니다.

용량 부족은 크기·영역 단위로 발생합니다

같은 가용 영역에서 g6e.8xlarge는 생성되지 않는데 g6e.16xlarge는 뜨는 식입니다. 일시적이라 잠시 뒤 다시 시도하면 되는 경우가 많습니다.

판매 목록과 할당량 확인으로는 알 수 없습니다

"이 영역에서 이 크기를 파는가", "내 할당량이 충분한가"에만 답합니다. 현재 실제 여유 용량이 있는지는 노드를 생성해 봐야 확인됩니다. 시험 실행 (--dry-run)도 품절 조합에 성공을 반환합니다.

사용자가 할 수 있는 대응 3가지

  1. 대기열 제한 시간을 늘려 두고 기다립니다 — queue_timeout을 충분히 지정하면 용량이 확보되는 시점에 자동으로 실행됩니다. 기본값 1시간으로는 부족한 경우가 있습니다
  2. 다른 장비로 바꿉니다 — --set platform=g7e-rtx-pro-6000. 96GB 장비 쪽에 여유가 있을 수 있습니다. 반대 방향도 마찬가지입니다
  3. 관리자에게 전달합니다 — 가용 영역 추가, 리전 변경, 할당량 증설은 사용자 권한으로 할 수 없습니다

학습 지표를 대시보드에 남기기

GPU 사용률·메모리·온도는 자동으로 대시보드에 올라갑니다. 하지만 loss, 학습률 같은 학습 지표는 워크플로가 직접 내보내야 보입니다.

자동으로 올라가는 것

  • GPU 사용률 · 그래픽 메모리 사용량 · 전력 · 온도
  • 워크플로 상태와 로그

GPU를 감시하는 구성 요소가 노드마다 떠 있어서, 사용자가 아무것도 하지 않아도 수집됩니다.

직접 내보내야 하는 것

  • loss · 학습률 · epoch · 기울기 크기
  • 강화학습 보상, 평가 성공률 등 코드가 계산하는 값

학습 코드가 표준 출력에만 기록하는 값은 로그에만 남고 대시보드로 전달되지 않습니다.

보내는 방법 — 학습 출력을 중계 스크립트에 흘려보냅니다

files:
- path: /tmp/push_metrics.py
  contents: |
    # scripts/push_metrics.py 내용을 그대로 붙여 넣습니다

# 태스크 스크립트
PUSHGATEWAY_URL="{{ pushgateway_url }}"   # 비어 있으면 전송을 건너뜀 — 지표 없음
METRICS_JOB="groot_training"              # 단계마다 하나씩 다르게
WORKFLOW_ID="${HOSTNAME}"                 # 실행별로 구분되는 이름

python train.py ... 2>&1 \
  | PUSHGATEWAY_URL="${PUSHGATEWAY_URL}" METRICS_JOB="${METRICS_JOB}" \
    WORKFLOW_ID="${WORKFLOW_ID}" python3 -u /tmp/push_metrics.py

3단계 미세조정 워크플로에 이미 들어 있습니다 (e2e-pipeline-examples/03-vla-finetune/workflow.yaml). 새 워크플로를 쓸 때는 여기서 복사하면 됩니다 — 워크플로 파일은 다른 파일을 불러올 수 없어 매번 붙여 넣어야 합니다.

워크플로 이름 — workflow.name

workflow:
  name: aws-e2e-data-prep

이 리포의 규칙: aws- 접두사 + 무엇을 하는지. 제출하면 뒤에 번호가 붙어 aws-e2e-data-prep-12가 되고, 상태와 로그를 볼 때는 번호가 붙은 이 이름을 씁니다.

outputs:

실패 시 점검 순서

동일한 오류 코드라도 원인 계층이 다릅니다. 네트워크 → 인증 → 제출 → 스케줄링 → 실행 순으로 확인하면 대부분 두세 단계에서 원인이 확정됩니다.

  1. 엔드포인트 연결 확인 — curl로 /api/version 응답 코드를 확인합니다. 403이면 인증 실패가 아니라 웹 방화벽(WAF) 허용 IP 목록 미등록입니다
  2. 인증·인가 확인 — osmo workflow list의 응답을 확인합니다. 연결은 되지만 403이면 역할(role) 미부여입니다
  3. 제출 처리 확인 — 제출 응답에 워크플로 이름이 반환됐는지 확인합니다. YAML 문법 오류와 스키마 오류는 이 단계에서 검출됩니다
  4. 스케줄링 상태 확인 — osmo workflow query로 상태를 확인합니다. 대기(Pending)가 길면 노드 용량 부족, 실패(Failed)면 다음 단계로 진행합니다
  5. 컨테이너 실행 로그 확인 — osmo workflow logs로 확인합니다. 이 단계부터는 사용자 코드와 이미지 영역의 문제입니다

플랫폼 영역 오류

403 응답, 장시간 Pending, 노드 프로비저닝 실패. 관리자에게 전달합니다 — 사용자 권한으로는 해결할 수 없습니다

사용자 영역 오류

이미지 다운로드 실패, 실행 파일 경로 오류, 파이썬 예외, 메모리 부족(OOM). YAML과 코드를 수정해 해결합니다

액세스 토큰 만료 시에도 모든 명령이 실패합니다. 이 경우 scripts/osmo-cli-login.sh를 다시 실행해 재인증합니다.

효과가 있는 쪽

  • 설정값 추적 — 이 값이 YAML에서 컨테이너 안 명령까지 어떻게 전달되는지 따라가는 일

  • YAML 초안 — 기존 예제를 읽혀서 비슷한 구조를 만드는 일

사람이 판단해야 하는 쪽

  • 용량 예측 — 지금 GPU를 구할 수 있는지는 아무도 모릅니다. 노드를 생성해 봐야 확인됩니다
  • 학습이 충분한지 — 지표는 읽어 주지만 "이 정도면 되는가"는 도메인 판단입니다. 이 리포에서도 성공률 0%의 원인 추정을 두 번 틀렸습니다

Q & A

부록 — 참조 아키텍처의 확장 항목

여기부터는 이 환경에 배포돼 있지 않은 항목입니다. 원본 발표 자료의 참조 아키텍처가 제시한 확장 방향이며, OSMO가 제공하는 기능이 아닙니다.

다루는 항목

  • 온프레미스 GPU와 클라우드 GPU의 이원화 문제
  • 온프레미스 장비 통합 — EKS Hybrid Nodes
  • 데이터 저장 계층과 모델 레지스트리
  • 분산 학습 프레임워크, 대화형 개발 환경, 고성능 파일 시스템

부록을 포함한 이유

현재 구성이 어디까지 확장될 수 있는지를 정리한 내용입니다. 규모가 커질 때 추가로 필요한 구성 요소를 미리 확인해 두는 용도입니다.

여기 나오는 이름을 platform 값으로 지정해도 배치되지 않습니다.

본 교육에서 실제로 제출하는 워크플로는 온디맨드 GPU 하나를 씁니다. 부록의 구성은 설명용입니다.

부록 — GPU 자원 이원화 문제

클라우드로 전환하면 기존 온프레미스 GPU 자산이 남습니다. 이를 방치하면 연구원의 작업 방식이 두 갈래로 나뉩니다.

미통합 시

클라우드 GPU는 OSMO로 제출, 기존 온프레미스 GPU는 별도 절차. 연구원이 두 가지 사용법을 익혀야 하고, 할당량도 서로를 모릅니다.

통합 시

온프레미스 장비를 같은 클러스터의 노드로 편입(EKS Hybrid Nodes). 연구원은 하나의 인터페이스에서 GPU 목표만 바꿉니다.

오해하기 쉬운 지점 — OSMO가 SageMaker HyperPod에 작업을 보내는 것이 아닙니다. HyperPod을 EKS 모드로 만들어 같은 쿠버네티스 클러스터의 노드로 편입해야 하고, 그러면 OSMO는 그 노드를 다른 노드와 똑같이 봅니다. 사용자에게 보이는 차이는 platform 값 하나입니다.

부록 — 온프레미스 장비의 클러스터 통합

사용자가 직접 다루는 영역은 아니지만, 온프레미스 GPU를 동일한 방식으로 사용할 수 있는 근거입니다. 네트워크를 연결해 클러스터 노드로 등록합니다.

필요 조건

  • 온프레미스 노드용·파드용 주소 범위를 클러스터에 미리 등록
  • 양쪽 라우팅 표에 서로의 경로 추가
  • 전용 회선 또는 가상 사설망(VPN)으로 연결

주의 — 이 리포 미포함 항목

하이브리드 노드 구성은 참조 아키텍처의 항목이며 osmov2 배포에는 포함되지 않습니다. 현재 클러스터의 노드는 전부 AWS 안에 있습니다.

체크포인트를 어디에 저장할지에 대한 기준입니다. 학습 중에는 빠른 저장소를, 보관에는 영구 저장소를 사용합니다.
